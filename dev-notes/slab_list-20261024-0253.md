# SlabList 设计记录（20261024-0253）

## 背景

旧 `Arena<T>` 基于 `slab` crate，向调用者返回 `Idx<T>`。B+ Tree 的节点通过
`Idx<T>` 再访问 `Arena`，每次比较或取值都需要把 arena 引用一路传下去。

本轮希望换一种分配策略：

- 不再逐元素分配，而是一次分配一个可容纳多个 `T` 的 **Chunk**；
- Chunk 头本身也构建在同一片内存上；
- 多个 Chunk 用 `prev` / `next` 指针组成双向链表；
- 槽位可以乱序归还；
- Arena 直接向调用者返回元素句柄，而不是索引；
- Chunk 内存可以由外部指定的 `Allocator` 分配。

本轮只实现独立的 `slab_list_` 模块和单元测试，暂不接入 `BPlusTree`，也暂不移除
`slab` 依赖。

## 已确认的决策

### 1. 配置按“单 Chunk 总字节数”，布局按需计算

`SlabListConfig` 只保存 `chunk_bytes`。具体布局在需要时根据 `T` 计算：

```text
slot_offset = align_up(size_of::<ChunkHeader>(), align_of::<Slot<T>>())
slots       = (chunk_bytes - slot_offset) / size_of::<Slot<T>>()
```

约束：

- `slots >= 1`，否则返回 `ChunkTooSmall`；
- `slots <= 2^15`，否则返回 `TooManySlots`；
- 布局无法表示时返回 `LayoutOverflow`。

`SlabList` 不缓存 `chunk_bytes`、`chunk_layout`、`slot_offset` 或
`slots_per_chunk`。它只保存 `SlabListConfig`，在 `insert`、`remove`、`drop`
等需要时重新计算 `ChunkLayout`。`new_in` 在构造时做一次校验，之后的计算
不可能失败。

Chunk 采用懒分配：`SlabList::new_in` 只校验配置，不分配内存；第一次 `insert`
才分配第一个 Chunk。

### 2. 不保存使用统计字段

`SlabList` 不保存 `len`、`capacity` 或 `chunk_count` 等使用统计字段，也不提供
对应的查询方法。它只负责管理 Chunk 链表、槽位分配和归还：

```rust
pub struct SlabList<T, A = Global>
where
    A: Allocator,
{
    head_: *mut ChunkHeader,
    tail_: *mut ChunkHeader,
    config_: SlabListConfig,
    allocator_: A,
    _marker_: PhantomData<Slot<T>>,
}
```

### 3. 外部 Allocator

`SlabList<T, A = Global>` 的 `A` 是 `core::alloc::Allocator`。默认使用
`Global`：

- `SlabList::new(config)` / `with_default_config()`：默认 `Global`；
- `SlabList::new_in(config, allocator)` / `with_default_config_in(allocator)`：
  使用外部 allocator。

Chunk 分配通过 `Allocator::allocate`，释放通过 `Allocator::deallocate`。
分配失败时调用 `handle_alloc_error`，与默认 `Global` 的行为一致。

### 4. Chunk 内存布局

```text
+----------------------+  <- 分配基址
| ChunkHeader          |
|  prev / next         |
|  free_head: u16      |
|  free_count: u16     |
|  capacity: u16       |
+----------------------+  <- slot_offset
| Slot<T> #0           |
|  value: MaybeUninit  |
|  self_idx: u16       |
|  next_free: u16      |
+----------------------+
| Slot<T> #1           |
| ...                  |
+----------------------+
```

`Slot<T>` 使用 `#[repr(C)]`，`value` 位于槽位起始地址，因此：

- 指向元素的 `*mut T` 同时也是槽位基址；
- 槽位尾部的两个 `u16` 紧跟在 `T` 后面（ZST 时允许偏移为 0）。

### 5. `self_idx` 最高位作 occupied 标记

槽数上限取 `2^15`，而不是 `u16::MAX`，原因是：

- `self_idx` 低 15 位保存槽号；
- `self_idx` 最高位保存 occupied 标记；
- `next_free == u16::MAX` 表示空闲链表结束。

这样 `drop` 可以顺序遍历所有槽位，通过 occupied 位区分“存活元素”和“空闲槽位”，
不需要先遍历空闲链表做标记。

`next_free` 只保存下一个空闲槽号，不参与 occupied 判断。

### 6. `SlotPtr<T>` 只保存 `NonNull<T>`

`SlotPtr<T>` 是一个 `Copy` 的透明句柄，内部只有 `NonNull<T>`，并实现
`Deref` / `DerefMut`。它可以直接存入 B+ Tree 节点，解引用时不再需要 arena 引用。

`remove` 的 O(1) 反向定位过程：

```text
slot_base = ptr as *mut u8
self_idx  = read(slot_base + offset_of!(Slot<T>, self_idx))
idx       = self_idx & 0x7FFF
slot0     = slot_base - idx * size_of::<Slot<T>>()
chunk     = slot0 - slot_offset
```

因此不需要扫描 Chunk 链表。代价是句柄有效性由调用者维护，详见“安全约定”。

### 7. Chunk 链表的近似排序

不按 `free_count` 严格排序，而是：

- 有空闲槽位的 Chunk 尽量在链表头部；
- 某个 Chunk 被写满后移到链表尾部；
- 某个 Chunk 归还槽位后移到链表头部。

因此链表头部始终是可分配的 Chunk（如果还有可分配 Chunk），但它不一定是空闲槽
数量最多的 Chunk。这是“尽量把空闲最多的 Chunk 放在头部”的近似实现，避免了每次
分配/归还都维护严格有序链表的成本。

### 8. 归还与析构

- `remove(ptr) -> T`：先从槽位中 `read` 出 `T`，再清 occupied 位，把槽位压入所属
  Chunk 的空闲链表头部，并把 Chunk 移到链表头部。
- 空闲链表是 LIFO，因此刚释放的槽位会优先被复用。
- `Drop for SlabList` 遍历 Chunk 的所有槽位，只对 occupied 位为 1 的槽位执行
  `drop_in_place`，然后使用构造时的 allocator 释放整个 Chunk 分配。
- 重复 `remove` 会在 occupied 位检查处 panic，避免静默破坏空闲链表。

### 9. ZST 支持

`Slot<T>` 即使 `T` 是 ZST，也包含两个 `u16` 元数据，因此槽位大小至少为 4 字节，
每个槽位仍然有独立地址。

`SlotPtr` 指向槽位基址，而不是 `MaybeUninit<T>::as_mut_ptr()` 可能返回的悬垂地址。
由于 `value` 位于槽位起始地址，ZST 也能通过 `self_idx` 正常反推 Chunk。

## 公开 API

```rust
pub struct SlabListConfig { /* chunk_bytes */ }
impl SlabListConfig {
    pub const MAX_SLOTS_PER_CHUNK: usize = 1 << 15;
    pub const fn new(chunk_bytes: usize) -> Self;
    pub const fn chunk_bytes(&self) -> usize;
    pub fn slots_per_chunk<T>(&self) -> Result<usize, SlabListError>;
}

pub struct SlabList<T, A = Global> { /* head, tail, config, allocator */ }

impl<T> SlabList<T, Global> {
    pub fn new(config: SlabListConfig) -> Result<Self, SlabListError>;
    pub fn with_default_config() -> Result<Self, SlabListError>;
}

impl<T, A> SlabList<T, A>
where
    A: Allocator,
{
    pub fn new_in(config: SlabListConfig, allocator: A) -> Result<Self, SlabListError>;
    pub fn with_default_config_in(allocator: A) -> Result<Self, SlabListError>;
    pub const fn config(&self) -> SlabListConfig;
    pub const fn allocator(&self) -> &A;
    pub fn slots_per_chunk(&self) -> usize;
    pub fn insert(&mut self, value: T) -> SlotPtr<T>;
    pub fn remove(&mut self, ptr: SlotPtr<T>) -> T;
}

pub struct SlotPtr<T> { /* NonNull<T> */ }
impl<T> Deref for SlotPtr<T> { type Target = T; }
impl<T> DerefMut for SlotPtr<T> { /* ... */ }
```

## 安全约定

`SlotPtr` 是无生命周期的 `Copy` 裸指针句柄，类型系统无法约束它的有效期。调用方必须：

- 只使用由仍然存活的同一 arena 的 `insert` 返回的句柄；
- 不在槽位已经 `remove` 后继续解引用（除非它被重新插入）；
- 不同时通过多个句柄创建别名 `&mut T`；
- 不在 `SlabList` drop 后继续使用句柄。

`remove` 会对 occupied 位做检查，因此同一槽位的重复归还会 panic；但把其他 arena
的句柄或悬垂句柄传给 `remove` 属于逻辑错误，可能触发未定义行为。这是为了换取
O(1) 反向定位、避免 Chunk 链表扫描而接受的取舍。

## 测试覆盖

`src/slab_list_/list_.rs` 中包含以下中英双语单元测试：

- 过小和槽数超限的配置被拒绝；
- 基本插入、`Deref` / `DerefMut`、乱序归还；
- 空闲链表 LIFO 复用；
- Chunk 扩容、写满移尾、从中间/尾部释放后移回头部并复用；
- `drop` 只析构存活元素，不重复析构空闲槽位；
- ZST 槽位地址互异且可归还；
- 重复 `remove` panic；
- 默认配置；
- 外部 allocator 的分配/释放次数。

以上 10 个单元测试已通过 `cargo test slab_list_`、`cargo test`（含文档测试）
与 `cargo miri test slab_list_`；`cargo clippy --all-targets` 对新模块无告警。

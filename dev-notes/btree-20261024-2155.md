# B Tree 实现设计记录（20261024-2155）

## 背景

B+ Tree 已经完成，公开 API 以 Comparer 定序、避免复制 Key、用 SlabList 批量分配
节点。本轮在同样的原则下新增标准 B Tree：

- 排序仍然完全由 `TrComparer` 定义；
- 查询类型可以与 `K` 不同；
- 节点全部由 SlabList 分配，避免逐节点堆分配造成的长期碎片；
- 公开 API 与 `BPlusTree` 保持对称，方便使用者切换。

与 B+ Tree 的关键区别是：B Tree 的所有节点都可以保存实际数据，索引节点不再只是
“分隔 key + 孩子”。

## 已确认的技术决策

### 1. 数据直接存入节点，只使用一个 node SlabList

B+ Tree 使用两个 SlabList：

```text
data SlabList: (K, V)
node SlabList: TreeNode（只保存 SlotPtr）
```

B Tree 改为：

```text
node SlabList: Node
                    └── OrderedArray<M, K, NodeValue>
                                  ├── K
                                  └── NodeValue { V, right_child }
```

原因：

- 标准 B 树的每个节点都可以保存数据，数据不需要单独的数据 arena；
- 每个 `(K, V)` 只存在一份，键值在节点之间移动时使用 move，不复制，仍然满足
  “Key 不需要 Clone”；
- 只需要一个 SlabList，内存来源更集中；
- 节点数组的排序键就是实际 `K`，Comparer 直接是 `TrComparer<K>` /
  `TrComparer<K, Q>`，不需要 Entry 适配器。

代价是分裂/借位/合并时会移动 `(K, V)`，因此不承诺 `&K` 的地址稳定；这与 B+ Tree
的“数据地址稳定、索引只移动 SlotPtr”不同。Rust 的借用规则保证调用方不能同时持有
`&K` 和 `&mut tree`，所以移动本身是安全的。

### 2. 统一节点布局

```rust
pub(crate) struct NodeValue<const M: usize, K, V> {
    value_: V,
    right_: Option<TreeNodePtr<M, K, V>>,
}

pub(crate) struct Node<const M: usize, K, V> {
    first_child_: Option<TreeNodePtr<M, K, V>>,
    entries_: OrderedArray<M, K, NodeValue<M, K, V>>,
}
```

- `first_child_` 为 `Some` 表示内部节点；
- 第 `i` 项的右孩子是第 `i + 1` 个孩子；
- 内部节点最多 `M` 个项、`M + 1` 个孩子；
- 叶子节点 `first_child_` 与所有 `right_` 都是 `None`。

不能把 `children_` 写成 `OrderedArray<{M + 1}, ...>`，因为稳定版 Rust 不支持在
数组长度中使用泛型常量表达式。`first_child_ + M 个 right_` 正好表达 `M + 1` 个
孩子，且不需要额外的 `M + 1` 容量。

### 3. 节点容量与最小占用

`M` 表示每个节点最多保存的项数，要求 `M >= 2`。

- 内部节点最多 `M + 1` 个孩子；
- 非根节点至少有 `ceil((M + 1) / 2)` 个孩子，即
  `min_keys = ceil((M + 1) / 2) - 1` 个项；
- 根节点豁免，非空 root 至少有 1 个项；
- 分裂时把“已满的 M 项 + pending 1 项”视为 `M + 1` 项，中间项上移，
  左半 `mid = ceil(M / 2)` 项，右半 `M - mid` 项。

对于偶数 `M`，满节点只有 `M` 项，不能直接均分成两个合法节点；必须把 pending 项
纳入分裂，得到 `M + 1` 项。实现中不实际创建 `M + 1` 容量的数组，而是先移动右侧
项到新数组，再决定 pending 落在左、右，或成为上移项。这样 `M = 2` 也能正确工作。

### 4. 插入：pending 分裂与位置追踪

插入采用递归回溯：

1. 叶子未满：直接插入；
2. 叶子已满：`split_node_with_pending_` 把 pending 合并进分裂过程，返回上移项和新
   右节点；
3. 父节点未满：插入上移项，结束；
4. 父节点已满：把上移项当作新的 pending，继续分裂；
5. 根分裂：创建新的内部 root。

待插入项可能上移到祖先节点（例如 `M = 2` 时，原根 `[1, 3]` 插入 `2`，`2` 成为
新 root 的唯一项）。因此分裂结果包含 `PendingPlace`，逐层跟踪 pending 最终
位置，`try_insert` / `try_insert_by` 可以直接返回正确的 `(&K, &mut V)`，不需要
插入后重新查找。

### 5. 删除：递归回溯修复

删除采用递归，而不是 B+ Tree 的显式 path SlabList：

1. 在节点中二分查找；
2. 若命中内部节点，取右子树最小项替换该项，再从右子树删除最小项；
3. 递归返回后检查子节点是否低于 `min_keys`；
4. 优先向左兄弟借、再向右兄弟借，否则与兄弟合并；
5. 合并后父节点可能继续下溢，由上一层修复；
6. 删除完成后，若 root 为空内部节点，提升其唯一孩子。

递归深度由最小 fanout 保证为 `O(log n)`：非根内部节点至少 2 个孩子。即使
`M = 2` 退化，树高也只有 `O(log n)`，不会像显式 path 那样需要处理任意长的链。
因此这里不需要 `SlabList<PathFrame>`；节点本身仍然全部来自 SlabList。

删除内部项时先替换、后修复右子树，最后才把返回的 `(K, V)` 交给调用方。数据一直
在节点中，直到 `OrderedArray` 真正移除该项，因此不会出现 B+ Tree 中“separator
仍指向已释放数据槽位”的问题。

### 6. 迭代：父指针中序后继

B Tree 数据分散在所有层级，不能沿叶子链迭代。节点保存 `parent_` 父指针后，
`BTree::iter()` 直接计算中序后继：

- 当前项在内部节点中时，后继是右子树的最小项；
- 当前项在叶子中时，后继是同叶子的下一项；
- 叶子最后一项则沿父链找到第一个“当前孩子不是最后一个孩子”的祖先，取该祖先
  中对应的项。

迭代器只保存当前 `(节点, 下标)`，不使用工作栈，也没有 `Vec` 或其他堆分配。

### 7. 公开 API 对称与命名

根级已经导出 B+ Tree 的 `ConflictInfo` 与 `TreeIter`，为避免类型名冲突：

```text
bplustree_cmp::BTree
bplustree_cmp::BTreeConflictInfo   （btree::ConflictInfo 的别名）
bplustree_cmp::BTreeIter           （btree::TreeIter 的别名）
bplustree_cmp::btree::{BTree, ConflictInfo, TreeIter}
```

B Tree 的方法集与 B+ Tree 完全对应：

```text
BTree
├── new_in, degree, len, is_empty, comparer
├── first, last
├── get, get_mut, get_by, get_mut_by
├── try_insert, try_insert_by, insert
├── remove, remove_entry, remove_by, remove_entry_by
├── iter -> TreeIter
└── from_iter_by

ConflictInfo
├── existing, conflict
└── into_parts, into_existing, into_conflict

TreeIter: Iterator + ExactSizeIterator + FusedIterator
Extend<(K, V)>、FromIterator<(K, V)>（要求 C: Default）
IntoIterator for &BTree
```

`M` 在 B+ Tree 与 B Tree 中都表示“每个节点最多保存的项数”，但内部节点孩子上限
不同：B+ 树索引节点最多 `M` 个孩子，B 树内部节点最多 `M + 1` 个孩子。`degree()`
返回 `M`，文档中明确说明这一点。

### 8. 比较器适配

节点数组类型是 `OrderedArray<M, K, NodeValue<M, K, V>>`，排序键就是真实 `K`。
因此：

- `try_insert_pair_by((K, NodeValue), &C)` 中 `C: TrComparer<K>`；
- `binary_search_by(query, &C)` 中 `C: TrComparer<K, Q>`；
- 不需要 B+ Tree 的 `SlotPairKeyComparer` / `QuerySlotComparer` 这类 Entry 适配器。

这减少了间接层，也让 B Tree 的比较路径比 B+ Tree 更短（B+ Tree 每次比较需要
解引用 `SlotPtr<(K, V)>`）。

## 与 B+ Tree 的差异

| 项目 | B+ Tree | B Tree |
| --- | --- | --- |
| 数据位置 | 只在叶子 | 所有节点 |
| SlabList 数量 | data + node (+ path) | node |
| 索引节点内容 | separator `SlotPtr` + 孩子 | `(K, V)` + 右孩子 |
| 数据地址稳定性 | 稳定 | 随节点移动 |
| 迭代 | 叶子链 | 父指针中序后继 |
| 插入/删除路径 | 父指针向上传播 | 递归 + 父指针修复 |
| 比较开销 | 解引用 SlotPtr | 直接比较节点内 K |

# B+ Tree 实现设计记录（20261024-0433）

## 背景

`slab_list_` 接入后，`BPlusTree`、`node_`、`search_` 仍是骨架：搜索、插入、分裂、
删除、迭代均未实现。本轮在保留以下特性的前提下补完 B+ 树：

- `K` 不需要 `Ord` / `PartialOrd` / `Eq`；
- 查询类型可以不是 `K`；
- 索引节点不复制 `K`，只保存 `SlotPtr<(K, V)>`；
- 排序完全由 `TrComparer` 定义；
- 数据与节点分别存放在两个 `SlabList` 中。

参考 C# `SortedDictionary` 的**对外 API 思路**：暴露 comparer、支持从已有集合构建、
提供按序迭代；内部结构仍然是 B+ 树，而不是红黑树。

## 已确认的技术决策

### 1. Separator 的语义：子树最大 key 的 SlotPtr

每个索引项为：

```text
(sep: SlotPtr<(K, V)>, child: TreeNodePtr)
```

其中 `sep` 是 `child` 子树中最大 key 的引用。

搜索规则：

- 在索引节点上取第一个 `sep >= query` 的孩子；
- 如果所有 `sep < query`，走最后一个孩子；
- 查询落在两个子树之间的空档时，进入后一个孩子；插入到该孩子头部仍然正确。

这样索引节点不拥有 Key，只在删除子树最大 key 时需要沿 path 更新祖先 separator。
这是“不复制 Key”的直接代价，必须用 path 栈完成。

### 2. TreeNode 内部重构

旧结构有四个问题：

1. `RootNode` 与 `IndexNode` 都只是 `(separator, child)` 数组，Root 只多一个
   `LeafSentinel`，搜索/分裂/根收缩需要两套分支；
2. `IndexNode::parent_` 非空，根的直接孩子没有真实父节点，只能塞 dummy；
3. `DataLeaf::prev_sibl_` / `next_sibl_` 非空，首尾叶只能用测试专用
   `dangling_for_test_()` 占位；
4. `TrPickKeyPolicy` / `IndexKeyComparer` / `IndexOrdKeyComparer` 是“不保存
   separator、临时取孩子 first/last key”的旧方案遗留，与当前设计矛盾且未使用。

因此改为：

```rust
pub(crate) enum TreeNode<const M: usize, K, V> {
    Index(IndexNode<M, K, V>),
    Leaf(DataLeaf<M, K, V>),
}

pub(crate) struct IndexNode<const M: usize, K, V> {
    children_: IndexPtrOrdArr<M, K, V>,
}

pub(crate) struct DataLeaf<const M: usize, K, V> {
    order_arr_: DataPtrOrdArr<M, K, V>,
    prev_sibl_: Option<TreeNodePtr<M, K, V>>,
    next_sibl_: Option<TreeNodePtr<M, K, V>>,
}
```

`BPlusTree` 自己持有：

```rust
root_: Option<TreeNodePtr<M, K, V>>,
first_leaf_: Option<TreeNodePtr<M, K, V>>,
last_leaf_: Option<TreeNodePtr<M, K, V>>,
```

- 删除 `RootNode`、`LeafSentinel`；
- 删除 `IndexNode::parent_`，搜索/插入/删除用显式 path 栈；
- 叶子兄弟指针改为 `Option`，边界不再需要 dummy；
- 删除旧 picking comparer。

README 中的特性列表不变；改变的只是内部树元数据的位置。root 可以是 `Leaf`，
也可以是 `Index`。

### 2.1 插入/删除路径改为 SlabList 分配的 PathFrame

最初实现使用 `Vec<(TreeNodePtr, usize)>` 保存从 root 到叶子的 path。它虽然简单，
但每次插入/删除都会产生一次堆分配，违背了 SlabList 控制长期内存碎片的初衷。

最终改为：

- 新增 `PathFrame`：`(node, child_idx, prev)`，大小固定；
- 新增 `Path`：只保存栈顶帧指针；
- 帧由独立的 `SlabList<PathFrame>` 分配，操作结束后全部归还；
- 帧按“叶子父节点 -> root”链接，正好对应自底向上的 separator 维护顺序；
- 不限制树高：即使 `M = 2/3` 出现退化的一元链，也只是增加 path 帧数量，
  不会退化成任意长度的堆分配；
- 帧的槽位会在后续操作中复用，长期运行时不会不断产生新的小对象。

代价是 path 的压栈/弹栈需要经过 SlabList 的槽位分配与回收，比 `Vec::push`
多一层间接；但内存来源与树节点一致，符合 Arena 的设计目标。

### 3. OrderedArray 只做增量扩展

`OrderedArray` 的双数组布局保持不变：

- `elems_` 物理存储；
- `order_` 逻辑顺序；
- 不变量：`order_[0..count_]` 为存活元素，`order_[count_..N]` 为空闲物理槽。

B+ 树删除的借位与合并需要删除任意位置，因此新增：

```rust
pub fn try_remove_at(&mut self, i: usize) -> Option<(K, V)>
pub fn try_remove_first(&mut self) -> Option<(K, V)>
```

`try_remove_at` 的实现：

1. 取出 `p = order_[i]` 并 `read` 出元素；
2. 左移 `order_[i+1..count_]`；
3. 把 `p` 放到 `order_[count_-1]`，再 `count_ -= 1`。

这样空闲物理槽仍在 `order_[count_..N]` 中，下一次插入会复用，`Drop` 也不会误析构。

不改成连续数组：现有布局已经支持非 `Copy` 元素的移动，且分裂只需
`try_remove_last + try_insert_pair_by`，没有必要扩大改动面。

### 4. 节点容量与最小占用

- `M`：每个节点的最大项数；叶子项数、索引孩子项数都不超过 `M`；
- 要求 `M >= 2`；
- 分裂时左侧保留 `(M + 1) / 2` 个原有项，右侧保留其余项，pending 项按 key
  插入其中一侧；
- 非根节点最小项数 `MIN = M / 2`（向下取整），根节点豁免。

偶数 `M` 会得到对称分裂；奇数 `M` 仍正确，只是填充率略不对称。

### 5. 插入流程

1. 从 root 下沉到叶子，记录 `(node, child_index)` path；
2. 叶子二分查重；冲突时不调用 factory；
3. 确认无冲突后调用一次 `factory`，写入 data arena；
4. 叶子未满直接插入；已满则用 pending 项分裂；
5. 自底向上更新 separator、插入新孩子项，必要时继续分裂；
6. 根分裂时创建新的 `Index` root。

分裂使用 pending 项，不引入 `M + 1` 临时容量。

### 6. 删除流程

1. 下沉并记录 path；
2. 叶子移除 `SlotPtr`；
3. 沿 path 把指向被删最大 key 的 separator 更新为新的子树最大 key；
4. 节点低于 `MIN` 时先借左右兄弟，否则合并；
5. 父节点可能继续不足，向上循环；
6. 根只剩一个孩子时收缩；
7. **所有 separator 更新完成后**才从 data arena 删除元素并返回 `(K, V)`。

第 7 条很重要：如果先删除 data，祖先中仍指向该槽位的 separator 会在比较时解引用
已释放内存。

### 7. 公开 API 风格

遵循 Rust 容器习惯，同时保留异构查询：

- `get` / `get_mut`：同构查询；
- `get_by` / `get_mut_by`：异构查询，显式传 comparer；
- `try_insert`：不覆盖已有值，冲突返回 `ConflictInfo`；
- `insert`：覆盖已有值，返回旧值；
- `remove` 返回 `Option<V>`；
- `remove_entry` 返回 `Option<(K, V)>`；
- `remove_by` / `remove_entry_by`：异构删除；
- `iter()` 返回按 key 升序的 `TreeIter`；
- `comparer()` 暴露 comparer；
- `from_iter_by` 从已有集合构建（重复 key 按 Rust `FromIterator` 习惯保留最后值）；
- `Extend<(K, V)>`。

`ConflictInfo` 同时服务两类插入：

- `try_insert_by` 在冲突时不调用 factory，`conflict` 为 `None`；
- `try_insert` 已经持有完整 pair，冲突时 `conflict` 为 `Some((K, V))`。

## 实现过程中发现的问题

### separator 传播提前终止

插入路径在子节点分裂后，会逐层更新父节点的 separator。最初实现中，
`old_parent_max` 是在 `set_separator_at_` **之后**读取的，导致：

- 如果 `set_separator_at_` 本身提高了父节点的最大 key；
- 随后又没有 pending 项需要插入；
- 那么 `new_parent_max == old_parent_max` 成立，循环错误地提前退出；
- 更高层的 separator 仍然指向旧的最大 key。

修复方式是**在 `set_separator_at_` 之前**读取父节点的旧最大 key，并在更新 separator
（以及可能的 pending 插入）之后比较。这样只要父节点最大 key 发生变化，就会继续
向上传播。

随机对拍测试（`M = 2..6`，2000 次操作）覆盖了这个问题；测试同时检查
`separator == 子节点子树最大 key`、节点占用、叶子链、首尾叶、迭代顺序和
`len`。

### 节点删除与 data 释放的顺序

删除时不能先 `data_arena_.remove(data_ptr)`：祖先 separator 可能仍然指向该
槽位，而借位/合并过程还会通过 Comparer 比较这些 separator。实现中先完成叶子
删除、separator 更新、借位/合并和根收缩，最后才从 data arena 删除并返回
`(K, V)`。

## 性能对比 Benchmark

新增 `benches/btreemap_compare.rs`（`harness = false`），与
`std::collections::BTreeMap<u64, u64>` 对比：

- 插入：随机顺序插入 N 个 key；
- 查询：随机命中查询与全部未命中查询；
- 迭代：遍历整棵树并累加 key/value；
- 删除：按随机插入顺序删除全部 key；
- 每个指标取多次采样的中位数，单位为 ns/op。

两种容器使用完全相同的 key 顺序和查询序列，避免数据分布差异。

一次 `N = 200000`、`samples = 5` 的本机结果（仅用于观察数量级）：

```text
operation          B+Tree(M=4)     B+Tree(M=16)        BTreeMap
insert                 1973.99          1758.03          447.07
lookup hit             1926.60          1862.02          481.68
lookup miss             153.46            89.91          103.63
iterate                  96.34            70.98           28.19
remove                 2232.97          1910.38          622.52
```

结论：

- 命中查询约慢 3.9x。根因是索引 key 为 `SlotPtr<(K, V)>`，每次比较需要解引用到
  Data SlabList；这是不复制 Key 的直接代价。
- 未命中查询在 `M = 16` 时反而更快，因为 B+ Tree 更浅。
- 插入/删除的祖先路径已改为由独立 `SlabList` 分配的固定 `PathFrame` 链，
  操作结束后归还帧，不再产生每次操作的 `Vec` 堆分配；只读查询使用
  不触碰 path 的 `find_leaf_`。
- 迭代沿叶子链进行，并逐个解引用数据句柄，因此慢于 `BTreeMap` 的节点内迭代。
- 对于大型 Key，避免复制的收益可能改变结论，后续可以针对 `String` 等类型补充
  benchmark。

## 模块边界调整

为后续实现同样基于 SlabList 的 B Tree，模块边界调整为：

```text
src/
├── comparer_.rs       独立 Comparer trait
├── slab_list_/        共享 Arena
├── ordered_arr_.rs    通用有序数组
└── bplus_tree_/
    ├── mod.rs
    ├── tree_.rs
    ├── node_.rs
    ├── search_.rs
    └── path_.rs
```

原则：

- `comparer_` 保持独立，不移动到 B+ Tree 模块；
- `slab_list_` 是两层树共享的 Arena，保持在 crate 根层；
- `ordered_arr_` 是通用的固定容量有序数组，B Tree 节点也可以复用，因此不锁进
  `bplus_tree_`；
- `tree_` / `node_` / `search_` / `path_` 都是 B+ Tree 专有实现，收拢到
  `bplus_tree_`；
- `bplus_tree_/mod.rs` 逐项导出 `BPlusTree`、`ConflictInfo`、`TreeIter`，不使用
  glob 导出；
- crate 根继续导出 `bplustree_cmp::BPlusTree` 等公开路径，因此外部 API 不变。

后续 B Tree 可以只依赖 `comparer_`、`slab_list_`、`ordered_arr_`，不会与
`bplus_tree_` 产生反向依赖。

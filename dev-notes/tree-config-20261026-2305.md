# 树的 TrConfig 配置（20261026-2305）

## 背景

此前两棵树的最后一个公开泛型参数是 `A: Allocator`，内部 arena 固定使用
`DefaultSlabList`，即 64 KiB Chunk。使用者只能替换 allocator，不能调整 Chunk
大小。

本轮把 allocator 与 Chunk 大小合并为公开的 `Cfg: TrConfig` 泛型参数，让使用者
可以选择单 Chunk 字节数。按上一轮讨论，`TrConfig` **不做 sealed**：内置配置只是
推荐值，使用者仍可自行实现。

## 公开 API

```rust
pub trait TrConfig {
    type Allocator: Allocator;
    const CHUNK_SIZE: usize;
}

pub struct SlabListConfig<const CHUNK_SIZE: usize, A = Global> { /* ZST */ }

pub type DefaultSlabConfig<A = Global> =
    SlabListConfig<DEFAULT_CHUNK_BYTES, A>;

pub struct BPlusTree<const M: usize, C, K, V = (), Cfg = DefaultSlabConfig>
where
    C: TrComparer<K>,
    Cfg: TrConfig;

pub struct BTree<const M: usize, C, K, V = (), Cfg = DefaultSlabConfig>
where
    C: TrComparer<K>,
    Cfg: TrConfig;
```

crate 根公开导出：

```text
TrConfig
SlabListConfig
DefaultSlabConfig
DEFAULT_CHUNK_BYTES
CHUNK_SIZE_1K .. CHUNK_SIZE_64K
```

`SlabList`、`SlabListError`、`SlotPtr`、`ChunkLayout` 仍保持 crate 内部。

## 使用方式

只选择 Chunk 大小、使用 `Global`：

```rust
use bplustree_cmp::CHUNK_SIZE_4K;
type Tree = BPlusTree<4, OrdComparer<u64>, u64, u64, SlabListConfig<CHUNK_SIZE_4K>>;
let tree = Tree::new().unwrap();
```

只替换 allocator、保持默认 64 KiB Chunk：

```rust
type Tree = BPlusTree<4, OrdComparer<u64>, u64, u64, DefaultSlabConfig<MyAlloc>>;
let tree = Tree::new_in(my_alloc).unwrap();
```

同时指定 Chunk 大小与 allocator：

```rust
type Tree = BPlusTree<4, OrdComparer<u64>, u64, u64, SlabListConfig<4096, MyAlloc>>;
let tree = Tree::new_in(my_alloc).unwrap();
```

`BPlusTree` 的 data arena 与 node arena 共用同一个 `Cfg::CHUNK_SIZE`。若未来需要
分别配置两个 arena，再引入 B+ Tree 专用配置类型。

## 构造器与类型推断

- `new()` / `with_comparer()` / `FromIterator` 要求
  `Cfg: TrConfig<Allocator = Global>`，但 Chunk 大小可以是任意值。
- `new_in()` / `with_comparer_in()` / `from_iter_in()` 接受
  `Cfg::Allocator`。
- 从 allocator 参数不能反推出 `Cfg`，因此
  `BPlusTree::<..., _>::new_in(alloc)` 这种写法不再可用；需要写出
  `SlabListConfig<CHUNK, _>` 或使用类型别名。
- 这是 `A` → `Cfg` 的主要迁移成本，已在 README 和 allocator 测试中体现。

## 约束与语义

- `CHUNK_SIZE` 是 Chunk 总分配字节数，不是槽位数。
- Chunk 至少需要容纳 ChunkHeader、对齐填充和一个 `Slot<T>`，否则树构造返回
  `TreeError`。
- 槽位数仍受 `MAX_SLOTS_PER_CHUNK = 2^15` 限制；Chunk 过大且 `T` 很小时可能
  返回 `TooManySlots`。
- 默认值仍为 64 KiB + `Global`，不改变现有默认行为的性能特征。
- crate 提供 `CHUNK_SIZE_1K`、`CHUNK_SIZE_2K`、`CHUNK_SIZE_4K`、
  `CHUNK_SIZE_8K`、`CHUNK_SIZE_16K`、`CHUNK_SIZE_32K`、`CHUNK_SIZE_64K`
  作为推荐档位，但本轮不引入 sealed trait，也不限制用户只能选择这些档位。

## 测试

新增 `tests/chunk_config.rs`：

- B+ Tree 的 data/node 两个 arena 的所有 Chunk 都使用配置的 4096 字节；
- B Tree 的所有 Chunk 都使用配置的 4096 字节；
- 用户自定义 `TrConfig`（8192 字节）可以正常构造和释放；
- 自定义 Chunk + `Global` 可以使用 `new()` / `FromIterator`；
- 过小 Chunk 返回 `TreeError`。
- Miri（strict provenance）通过全部 `tests/chunk_config.rs` 测试。

同时更新 `tests/allocator.rs` 的树类型显式写出
`SlabListConfig<DEFAULT_CHUNK_BYTES, _>`，验证自定义 allocator 仍可与默认
Chunk 大小组合。

验证：`cargo test`、`cargo clippy --all-targets -- -D warnings`、
`RUSTDOCFLAGS='-D warnings' cargo doc --no-deps` 全部通过。

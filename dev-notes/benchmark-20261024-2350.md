# 有序映射增删查改与遍历基准（20261024-2350）

## 目标

用同一组随机数据对比：

- `std::collections::BTreeMap<u64, u64>`；
- `BPlusTree<M, OrdComparer<u64>, u64, u64>`，`M = 4, 16`；
- `BTree<M, OrdComparer<u64>, u64, u64>`，`M = 4, 16`。

覆盖 `insert`、`lookup hit`、`lookup miss`、`update`（`get_mut`）、`iterate`、
`remove` 六类操作。

## 方法

`benches/btreemap_compare.rs` 继续使用 crate 内的自定义基准驱动，不引入
Criterion：

- 确定性 xorshift 生成随机 key 顺序、命中查询顺序与未命中查询顺序；
- `BENCH_N` 控制 key 数量，`BENCH_SAMPLES` 控制采样次数；
- 每个样本记录一次完整操作序列的耗时，取样本中位数，再除以操作数得到 ns/op；
- insert 的计时包含空容器构造；lookup/update/iterate/remove 的计时不包含
  容器构建或重建；
- 所有容器使用相同的 `ops`、`hits`、`misses` 序列；
- 用 `black_box` 避免校验和与结果被优化掉。

运行：

```text
cargo bench --bench btreemap_compare
BENCH_N=500000 BENCH_SAMPLES=7 cargo bench --bench btreemap_compare
```

## 本机结果

`N = 200000`、`samples = 5`，单位 ns/op（中位数）：

| lookup hit  |     1918.24 |      1785.82 |    1134.49 |     937.91 |   465.51 |
| lookup miss |      156.29 |        96.07 |     149.51 |      93.16 |   118.25 |
| update      |     1916.64 |      1788.81 |    1149.53 |     938.11 |   468.00 |

## 观察

- `M = 16` 在两棵树中通常都优于 `M = 4`，主要来自更浅的树高。
- B+ Tree 命中查询明显慢于 B Tree：B+ 的索引项是 `SlotPtr<(K, V)>`，每次比较
  需要解引用到 data arena；B Tree 的节点直接持有 `K`。
- 两类树仍慢于 `BTreeMap`，因为它们经由 `TrComparer` 做比较，并通过
  `SlabList` 管理节点；标准库使用更紧凑的节点布局和 `Ord` 直接比较。
- `M = 16` 的未命中查询略快于 `BTreeMap`，原因是树更浅、可以更早失败。
- 插入/删除需要处理 Chunk 分配、节点分裂/借位/合并，以及 B+ Tree 的 separator
  维护，因此成本显著高于 `BTreeMap`。
- 迭代沿叶子链或父指针完成，不使用额外 `Vec`；B+ Tree 仍比 B Tree 慢，因为需要
  逐项解引用数据句柄。

以上是 `u64 -> u64` 与默认 `Global` allocator 的结果，只用于观察数量级；大型 Key、
不同 allocator、不同 `M` 或不同数据分布可能改变结论。

# BPlusTreeCmp

一个基于 **Comparer 定义排序关系** 的 Rust B+ Tree 实现。

BPlusTreeCmp 的核心思想很简单：

> **数据是什么，与数据应该如何排序，是两件不同的事情。**

传统的 `BTreeMap<K, V>` 通常要求 `K: Ord`，排序关系属于 `K` 本身。

BPlusTreeCmp 则把排序关系从 Key 中抽离出来，由外部 `Comparer` 定义。

这带来了几个重要特性：

* **Key 不需要实现 `Ord`、`PartialOrd` 或 `Eq`**
* **查询类型不需要与 Key 相同**
* **查询时不需要构造一个 Key**
* **Key 不需要为了索引节点而 `Clone`**
* **内部索引节点不需要复制 Key**
* **同一个数据类型可以建立多种不同的排序索引**
* **数据、索引结构与排序关系彼此解耦**
* **Arena 对 B+ Tree 隐藏了具体的存储实现**

---

## 核心特点

### 1. Comparer 定义排序，而不是 Key

BPlusTreeCmp 使用：

```rust
pub trait TrComparer<A, B = A>
where
    A: ?Sized,
    B: ?Sized,
{
    fn compare(&self, a: &A, b: &B) -> Ordering;
}
```

B+ Tree 本身不要求：

```rust
K: Ord
```

只需要提供能够定义排序关系的 `Comparer`。

例如：

```rust
struct User {
    id: u64,
    name: String,
}
```

同一个 `User` 集合可以按照：

```text
id
name
其他业务字段
```

建立不同的索引，而不需要把某一种排序方式写死在 `User` 的 `Ord` 实现中。

因此，BPlusTreeCmp 更接近：

```text
Data + Ordering Relation
```

而不是简单的：

```text
Key: Ord
```

---

### 2. 天然支持异构查询

`TrComparer<A, B>` 的两个类型可以不同。

因此，树中保存：

```rust
String
```

可以直接使用：

```rust
&str
```

进行查询。

更进一步，树中保存：

```rust
User
```

并按照：

```rust
User.id
```

排序时，可以直接使用：

```rust
u64
```

作为查询对象。

不需要构造：

```rust
User {
    id: 123,
    name: String::new(),
}
```

只需要定义：

```rust
TrComparer<User, u64>
```

即可。

因此查询对象甚至可以**根本不是 Key 类型**。

---

### 3. Key 不需要 Clone

这是 BPlusTreeCmp 一个非常重要的实际优势。

传统 B+ Tree 的内部节点通常会保存 separator Key：

```text
Index Node

Key | Child
Key | Child
Key | Child
```

这意味着一个 Key 可能同时出现在：

```text
Leaf
Index
Higher Index
...
```

多个层级中。

当 Key 是：

```text
String
Vec<u8>
大型结构体
```

时，这种复制并不是免费的。

BPlusTreeCmp 则不把实际的 `(K, V)` 复制到索引节点。

数据只保存一次：

```text
Data Arena

(K, V)
(K, V)
(K, V)
...
```

索引节点保存的是：

```text
Idx<(K, V)>
```

以及对应的：

```text
TreeNodeId
```

因此：

> **索引节点引用 Key，而不是拥有 Key。**

所以 BPlusTreeCmp 不要求 `K: Clone`，也不需要因为构建索引而复制 Key。

---

### 4. IndexNode 不需要复制 Separator Key

B+ Tree 的内部节点真正需要解决的问题不是：

> “我必须保存一个 Key。”

而是：

> “给定一个查询对象，我应该进入哪个子树？”

传统实现通常通过复制一个 separator Key 来回答这个问题。

BPlusTreeCmp 使用另一种方式：

```text
IndexNode
    │
    ├── Idx<(K, V)> ────┐
    ├── Idx<(K, V)> ──┐ │
    ├── Idx<(K, V)> ┐ │ │
    │               │ │ │
    ▼               ▼ ▼ ▼
Data Arena
    │
    ├── (K, V)
    ├── (K, V)
    └── (K, V)
```

`Idx<(K,V)>` 是一个**类型化的数据引用**，不是 `(K,V)` 的副本。

索引数组可以通过 `Comparer` 对这些引用所指向的数据进行定序。

因此，索引节点可以保持非常轻量：

```rust
OrderedArray<
    M,
    Idx<(K, V)>,
    TreeNodeId<M, K, V>
>
```

这里的 `K` 仍然只存在于数据本身。

**IndexNode 不拥有一份额外的 Key。**

## 设计思路

BPlusTreeCmp 将整个问题拆成三个相互独立的部分：

```text
             Comparer
                 │
                 │ 定义顺序
                 ▼
        ┌─────────────────┐
        │    B+ Tree      │
        │                 │
        │  Index / Leaf   │
        └────────┬────────┘
                 │
                 │ typed index
                 ▼
              Arena
                 │
                 ▼
              Data
```

### Data

数据是：

```rust
(K, V)
```

它本身不负责定义排序。

### Comparer

Comparer 定义：

```text
K 与 K 如何比较
K 与 Query 如何比较
```

例如：

```rust
TrComparer<K>
TrComparer<K, Query>
```

排序关系属于索引，而不是数据类型本身。

### Index

Index 保存数据引用和树结构，而不是复制数据。

因此：

```text
Data
  └── (K, V)

Index
  └── Idx<(K, V)>
```

二者通过 typed index 连接。

# OrderedArray

B+ Tree 的 Root、Index 和 Leaf 节点内部都需要维护容量固定的小型有序数组。

BPlusTreeCmp 提供：

```rust
pub struct OrderedArray<const M: usize, K, V = ()>
```

它将：

```text
物理存储
```

与：

```text
逻辑排序
```

分离。

其中 Key 与 Value 是独立的：

```rust
OrderedArray<M, K, V>
```

并通过：

```rust
TrComparer<K, Query>
```

执行搜索和定序。

因此同一个 `OrderedArray` 可以支持：

```text
K ↔ K
K ↔ &str
K ↔ u64
K ↔ Query
```

只要存在相应的 Comparer。

# B+ Tree 的节点结构

当前树节点抽象为：

```rust
pub enum TreeNode<const M: usize, K, V> {
    Root(RootNode<M, K, V>),
    Index(IndexNode<M, K, V>),
    Leaf(DataLeaf<M, K, V>),
}
```

### Root

Root 保存子节点引用。

### Index

Index 保存：

```rust
OrderedArray<
    M,
    Idx<(K, V)>,
    TreeNodeId<M, K, V>
>
```

也就是说：

```text
Key
  ↓
Idx<(K,V)>
  ↓
实际数据
```

而 Value 是：

```text
TreeNodeId
```

因此 IndexNode 中的“排序 Key”实际上是一个数据引用。

**这里没有复制 Key。**

### Leaf

Leaf 保存：

```rust
OrderedArray<M, Idx<(K, V)>, ()>
```

也就是说 Leaf 同样通过 typed index 指向真正的数据。

这使得：

```text
Data
Index
Tree Structure
```

可以保持相对独立。

# 为什么这种设计仍然是 B+ Tree？

B+ Tree 的核心并不是：

> 每个 IndexNode 必须保存一组 Key 的副本。

它真正需要的是：

> 将有序数据空间划分为连续区间，并根据查询确定应该进入哪个子树。

Separator Key 只是表达这种区间划分的一种方式。

BPlusTreeCmp 则通过：

```text
数据引用 + Comparer
```

表达相同的信息。

因此：

```text
传统：

Separator Key
      ↓
决定子树


BPlusTreeCmp：

Idx<(K,V)>
      ↓
找到实际数据
      ↓
Comparer
      ↓
决定子树
```

两者表达的是同一个排序关系。

区别在于后者不会在 IndexNode 中复制 Key。

# Arena

BPlusTreeCmp 使用一个轻量的 `Arena<T>` 抽象保存对象，并通过：

```rust
Idx<T>
```

引用对象。

当前实现底层使用 `slab`，但 **B+ Tree 本身不依赖 `slab` 的接口**。

树看到的只是：

```rust
Arena<T>
Idx<T>
```

以及：

```rust
idx.get(&arena)
idx.get_mut(&mut arena)
```

这样的基本操作。

因此 Arena 是一个明确的抽象边界。

当前结构可以概括为：

```text
BPlusTree
   │
   ├── data Arena
   │       └── (K, V)
   │
   └── node Arena
           └── TreeNode
```

未来可以进一步将 Arena 独立出来，允许：

* 使用不同的 Arena 实现
* 使用外部 Arena
* 自定义对象生命周期管理
* 使用不同的内存分配策略
* 针对持久化、缓存或其他存储需求进行扩展

BPlusTree 本身不应该需要知道底层对象究竟由什么容器保存。

---

# Typed Index

`Idx<T>` 的核心作用是把：

```text
usize
```

变成带有类型信息的引用。

概念上：

```rust
Idx<T>
```

表示：

> “某个 `Arena<T>` 中对象的位置。”

它本身不拥有 `T`。

因此：

```rust
Idx<(K, V)>
Idx<TreeNode<M, K, V>>
```

虽然都是索引，但在类型系统中属于完全不同的类型。

这使得：

```text
Data Index
```

和：

```text
Node Index
```

不会被意外混用。

同时，`Idx<T>` 本身不要求 `T: Copy` 或 `T: Clone`；它只是一个带类型标记的索引值。

---

# Comparer 与 Index 的组合

Comparer 不仅可以比较实际数据：

```text
K ↔ K
```

也可以通过索引适配器参与：

```text
Idx<K> ↔ Idx<K>
```

或者异构地比较：

```text
Idx<L> ↔ Idx<R>
```

其基本思想是：

```text
Idx
 │
 ▼
Arena
 │
 ▼
实际对象
 │
 ▼
Comparer
 │
 ▼
Ordering
```

这使得“数据”“数据的引用”“查询对象”都可以进入统一的排序关系。

因此 Comparer 并不是一个单纯替代 `Ord` 的小接口，而是整个索引结构的基础抽象。

---

# 查询 API

BPlusTreeCmp 的查询模型不是：

```rust
tree.get(key)
```

而更接近：

```rust
tree.get_by(&query, &comparer)
```

其核心关系是：

```text
        Tree Data
            │
            │ K
            ▼
       Comparer<K, Q>
            ▲
            │ Q
            │
         Query
```

因此同一个数据集合可以存在多个查询关系。

例如：

```text
User
 ├── IdComparer
 ├── NameComparer
 ├── EmailComparer
 └── BirthdayComparer
```

甚至可以：

```text
User
   ▲
   │
u64 query
```

直接通过 `User ↔ u64` 的 Comparer 查询。

不需要改变 `User`，也不需要创建临时 `User`。

# 设计原则

BPlusTreeCmp 的设计可以归纳为以下原则：

### 1. 数据不负责排序

```text
Data ≠ Ordering Policy
```

排序关系由 Comparer 定义。

### 2. Index 不拥有 Key

Index 保存数据引用，而不是 Key 副本。

### 3. 查询不需要构造 Key

查询类型可以与 Key 完全不同。

### 4. Key 不需要 Clone

索引结构只保存 typed index，不复制实际 Key。

### 5. Data 与 Index 分离

数据和树节点分别存储，通过 `Idx<T>` 连接。

### 6. Arena 与 B+ Tree 解耦

树只依赖 Arena 抽象，而不依赖具体底层容器。

### 7. B+ Tree 负责结构，Comparer 负责顺序

B+ Tree 负责：

* 平衡结构
* 子节点组织
* 节点分裂与合并
* 搜索路径
* 叶节点组织

Comparer 负责：

* 小于
* 等于
* 大于
* 数据与查询之间的排序关系

# 与传统 `Ord` 型 B+ Tree 的区别

|                 | 传统设计         | BPlusTreeCmp            |
| --------------- | ------------ | ----------------------- |
| 排序关系            | Key 自己定义     | Comparer 定义             |
| `K: Ord`        | 通常需要         | 不需要                     |
| Key Clone       | 可能用于索引 Key   | 不需要                     |
| Index Separator | 通常保存 Key     | 保存数据引用                  |
| 查询类型            | 通常与 Key 紧密相关 | 可以完全不同                  |
| 异构查询            | 依赖额外机制       | `TrComparer<K, Q>` 原生支持 |
| 一个数据类型的多个排序     | 通常需要额外包装     | 可以提供多个 Comparer         |
| 数据与索引           | 容易耦合         | 明确分离                    |
| 底层存储            | 通常由结构直接决定    | 通过 Arena 抽象             |

# 当前状态

项目当前主要目标是实现和验证这种 **Comparer-first B+ Tree** 架构。

目前已经建立的核心基础包括：

* `TrComparer<A, B>` 排序抽象

完整的 B+ Tree 插入、节点分裂、删除、搜索以及更高层 API 仍在持续实现中。

因此当前项目更适合作为：

> **一种 Comparer-first、轻量索引、数据与排序关系解耦的 B+ Tree 架构实现。**

而不是已经完成的标准库 `BTreeMap` 替代品。

# 一句话总结

如果只用一句话概括 BPlusTreeCmp：

> **B+ Tree 不需要拥有 Key，它只需要拥有能够根据 Comparer 找到正确位置的索引。**

Comparer 让 Key 不必定义自己的排序，也让查询可以完全异构；Arena 和 typed index 则让索引可以引用数据而不是复制数据。

最终形成：

```text
                 Comparer
                    │
                    ▼
             Ordering Relation
                    │
                    ▼
             ┌─────────────┐
             │  B+ Tree    │
             │             │
             │ lightweight │
             │   Index     │
             └──────┬──────┘
                    │
                 Idx<T>
                    │
                    ▼
                  Arena
                    │
                    ▼
                 (K, V)
```

**数据只有一个来源，索引只是引用，排序属于 Comparer，查询不必成为 Key。**

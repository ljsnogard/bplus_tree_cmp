# BPlusTreeCmp

一个基于 **Comparer 定义排序关系** 的 Rust B+ Tree / B Tree 实现。

BPlusTreeCmp 的核心思想很简单：

> **数据是什么，与数据应该如何排序，是两件不同的事情。**

传统的 `BTreeMap<K, V>` 通常要求 `K: Ord`，排序关系属于 `K` 本身。BPlusTreeCmp 则把排序关系从 Key 中抽离出来，由外部 `Comparer` 定义。

这带来了几个重要特性：

* **Key 不需要实现 `Ord`、`PartialOrd` 或 `Eq`**
* **查询类型不需要与 Key 相同**
* **查询时不需要构造一个 Key**
* **Key 不需要为了索引节点而 `Clone`**
* **内部索引节点不需要复制 Key**
* **同一个数据类型可以建立多种不同的排序索引**
* **数据、索引结构与排序关系彼此解耦**
* **SlabList 对 B+ Tree 与 B Tree 隐藏了具体的存储实现**
* **两棵树都公开 `Cfg: TrConfig` 泛型参数，可同时选择 Chunk 大小与 allocator；SlabList 不要求 allocator `Clone`**
* **提供 `range` / `range_mut` / `iter_mut` / `keys` / `values_mut` 等与 `BTreeMap` 对应的迭代 API，且不引入临时堆分配**

## 核心特点

### 1. Comparer 定义排序，而不是 Key

BPlusTreeCmp 使用：

```rust
pub trait TrComparer<A, B = A>
where
    A: ?Sized,
    B: ?Sized,
{
    fn compare(&self, a: &A, b: &B) -> Ordering;
}
```

B+ Tree 本身不要求 `K: Ord`，只需要提供能够定义排序关系的 `Comparer`。

例如，`struct User { id: u64, name: String }` 这样的数据类型，同一个 `User` 集合可以按照 `id`、`name` 或其他业务字段建立不同的索引，而不需要把某一种排序方式写死在 `User` 的 `Ord` 实现中。

因此，BPlusTreeCmp 更接近 `Data + Ordering Relation`，而不是简单的 `Key: Ord`。

---

### 2. 天然支持异构查询

`TrComparer<A, B>` 的两个类型可以不同。树中保存 `String` 时可以直接使用 `&str` 查询；更进一步，树中保存 `User` 并按照 `User.id` 排序时，可以直接使用 `u64` 作为查询对象。

不需要构造 `User { id: 123, name: String::new() }`，只需要定义 `TrComparer<User, u64>` 即可。因此查询对象甚至可以**根本不是 Key 类型**。

---

### 3. Key 不需要 Clone

这是 BPlusTreeCmp 一个非常重要的实际优势。

传统 B+ Tree 的内部节点通常会保存一组 `Key | Child` 条目，因此一个 Key 可能同时出现在 `Leaf`、`Index`、`Higher Index` 等多个层级中。当 Key 是 `String`、`Vec<u8>` 或大型结构体时，这种复制并不是免费的。

BPlusTreeCmp 不把实际的 `(K, V)` 复制到索引节点。数据只保存一次，即 `Data SlabList` 中的若干 `(K, V)` 条目；索引节点保存的是 `SlotPtr<(K, V)>` 以及对应的 `TreeNodePtr`（即 `SlotPtr<TreeNode<M, K, V>>`）。

> **索引节点引用 Key，而不是拥有 Key。**

所以 BPlusTreeCmp 不要求 `K: Clone`，也不需要因为构建索引而复制 Key。

---

### 4. IndexNode 不需要复制 Separator Key

B+ Tree 的内部节点真正需要解决的问题不是“我必须保存一个 Key”，而是“给定一个查询对象，我应该进入哪个子树？”。传统实现通常通过复制一个 separator Key 来回答这个问题，BPlusTreeCmp 使用另一种方式：

```text
IndexNode
    │
    ├── SlotPtr<(K, V)> ────┐
    ├── SlotPtr<(K, V)> ──┐ │
    ├── SlotPtr<(K, V)> ┐ │ │
    │               │ │ │
    ▼               ▼ ▼ ▼
Data SlabList
    │
    ├── (K, V)
    ├── (K, V)
    └── (K, V)
```

`SlotPtr<(K, V)>` 是一个**类型化的数据引用**，不是 `(K, V)` 的副本。索引数组可以通过 `Comparer` 对这些引用所指向的数据进行定序，因此索引节点可以保持非常轻量：`OrderedArray<M, SlotPtr<(K, V)>, TreeNodePtr<M, K, V>>`。这里的 `K` 仍然只存在于数据本身。

**IndexNode 不拥有一份额外的 Key。**

---

## 设计思路

BPlusTreeCmp 将整个问题拆成三个相互独立的部分：

```text
             Comparer
                 │
                 │ 定义顺序
                 ▼
        ┌─────────────────┐
        │    B+ Tree      │
        │                 │
        │  Index / Leaf   │
        └────────┬────────┘
                 │
                 │ SlotPtr
                 ▼
              SlabList
                 │
                 ▼
              Data
```

### Data

数据是 `(K, V)`，它本身不负责定义排序。

### Comparer

Comparer 定义 `K ↔ K`、`K ↔ Query` 等比较关系，例如 `TrComparer<K>` 或 `TrComparer<K, Query>`。排序关系属于索引，而不是数据类型本身。

### Index

Index 保存数据引用和树结构，而不是复制数据：数据是 `(K, V)`，索引是 `SlotPtr<(K, V)>`，二者通过 SlotPtr 连接。

---

# OrderedArray

B+ Tree 的 Index 和 Leaf 节点内部都需要维护容量固定的小型有序数组。内部使用 `OrderedArray<const M: usize, K, V = ()>`，将物理存储与逻辑排序分离。其中 Key 与 Value 是独立的，类型为 `OrderedArray<M, K, V>`，并通过 `TrComparer<K, Query>` 执行搜索和定序。

因此同一个 `OrderedArray` 可以支持 `K ↔ K`、`K ↔ &str`、`K ↔ u64`、`K ↔ Query`，只要存在相应的 Comparer。

---

# B+ Tree 的节点结构

B+ Tree 的节点定义位于 `bplus_tree/node_.rs`。

当前树节点抽象为：

```rust
pub(crate) enum TreeNode<const M: usize, K, V> {
    Index(IndexNode<M, K, V>),
    Leaf(DataLeaf<M, K, V>),
}
```

其中 `TreeNodePtr<M, K, V>` 是 `SlotPtr<TreeNode<M, K, V>>` 的类型别名。
`IndexNode` 与 `DataLeaf` 都包含一个 `NodeBase`，其中的 `parent_` 指向父节点；
根节点为 `None`。插入和删除沿该父链向上维护 separator，不再需要 path 栈。

root 可以是 `Index`，也可以是 `Leaf`。root 指针、首叶和尾叶由 `BPlusTree` 自己持有：

```rust
root_: Option<TreeNodePtr<M, K, V>>,
first_leaf_: Option<TreeNodePtr<M, K, V>>,
last_leaf_: Option<TreeNodePtr<M, K, V>>,
```

这样不需要单独的 `RootNode` 变体。`IndexNode` 与 `DataLeaf` 都保存一个
`Option<TreeNodePtr>` 父指针，根节点为 `None`。插入和删除的向上传播直接沿父指针
完成，不再需要独立的 path 栈；父指针与树节点一样由 `SlabList` 管理。

### Index

Index 保存 `OrderedArray<M, SlotPtr<(K, V)>, TreeNodePtr<M, K, V>>`。也就是说，`Key` 先经 `SlotPtr<(K, V)>` 指向实际数据，而 Value 是 `TreeNodePtr`。每个索引项的分隔 key 是**孩子子树中最大 key 的引用**，因此 IndexNode 中的“排序 Key”实际上是一个数据引用，**这里没有复制 Key**。

### Leaf

Leaf 保存 `OrderedArray<M, SlotPtr<(K, V)>, ()>`，同样通过 SlotPtr 指向真正的数据。叶子通过 `Option<TreeNodePtr>` 类型的 `prev` / `next` 组成双向链，首叶没有前驱，尾叶没有后继。`Data`、`Index`、`Tree Structure` 因此可以保持相对独立。

---

# 为什么这种设计仍然是 B+ Tree？

B+ Tree 的核心不是“每个 IndexNode 必须保存一组 Key 的副本”，而是“将有序数据空间划分为连续区间，并根据查询确定应该进入哪个子树”。Separator Key 只是表达区间划分的一种方式；BPlusTreeCmp 通过 `数据引用 + Comparer` 表达相同信息：传统实现用 `Separator Key` 决定子树，而这里用 `SlotPtr<(K,V)>` 找到实际数据，再由 `Comparer` 决定子树。

搜索时在索引节点取第一个 `separator >= query` 的孩子；如果所有 separator 都小于 query，则走最后一个孩子。查询落在两个子树之间的空档时进入后一个孩子，插入到该孩子头部仍然正确。

由于 separator 是数据引用，删除某个子树的最大 key 时必须沿搜索路径把祖先中指向它的 separator 替换为新的最大 key，并且要等所有 separator 更新完成后才能从 Data SlabList 删除该元素。这是“不复制 Key”的直接代价，也是插入/删除需要沿父指针向上维护 separator 的原因。

两者表达同一个排序关系，区别在于后者不会在 IndexNode 中复制 Key。

# B Tree

同一 crate 还提供标准 B 树 `BTree`，其公开 API 与 `BPlusTree` 对称，但数据分布
在所有节点中，而不是只保存在叶子。

```rust
use bplustree_cmp::BTree;

let mut tree = BTree::<4, _, u64, &str>::new().unwrap();
tree.insert(2, "two");
tree.insert(1, "one");
assert_eq!(tree.first(), Some((&1, &"one")));
```

## 节点结构

B Tree 的节点定义位于 `btree/node_.rs`：

```rust
struct Node<const M: usize, K, V> {
    parent_: Option<TreeNodePtr<M, K, V>>,
    first_child_: Option<TreeNodePtr<M, K, V>>,
    entries_: OrderedArray<M, K, NodeValue<M, K, V>>,
}

struct NodeValue<const M: usize, K, V> {
    value_: V,
    right_: Option<TreeNodePtr<M, K, V>>,
}
```

- `entries_` 的排序键就是实际 `K`，所以 Comparer 直接是 `TrComparer<K>` /
  `TrComparer<K, Q>`，不需要 Entry 适配器；
- 每个项保存 `(K, V)` 和一个右孩子；
- `first_child_` 与 `M` 个右孩子一起表达最多 `M + 1` 个孩子；
- 叶子节点的 `first_child_` 与所有 `right_` 都是 `None`；
- 内部节点最多 `M` 个项，非根节点至少 `ceil((M + 1) / 2) - 1` 个项。

`(K, V)` 只存在一份。B 树在分裂、借位和合并时会把项按值移动到另一个节点，但
不会复制 Key；因此 `K` 仍然不需要 `Clone`。

这里需要区分“Node 槽位稳定”和“Node 内部的 `(K, V)` 地址稳定”：`SlabList` 只
保证它自己的槽位（也就是 `Node`）不会被移动；`(K, V)` 是内嵌在 `Node` 的数组
中的值，并不是独立分配的对象。分裂时，右半项会从原节点 `try_remove_*` 出来并
写入新节点；借位和合并时，项也会在父子或兄弟节点之间按值移动。因此同一个逻辑
项在修改操作后可能位于另一个节点的另一个数组槽位，不能承诺 `&K` 的地址稳定。

与之相对，B+ Tree 把 `(K, V)` 放在独立的 Data SlabList 槽位中，索引节点只移动
`SlotPtr`，所以数据地址在元素被删除前保持不变。

## 插入与删除

- 插入：满节点与待插入项组成 `M + 1` 个逻辑项，中间项上移，左右两半留在原节点与
  新节点；上移项可能继续向上传播，root 分裂时创建新 root。
- 删除：内部节点命中 key 时，用右子树最小项替换该项，再从右子树删除最小项；
  递归返回后按“先借位、后合并”的顺序修复下溢，最后收缩空 root。
- 节点全部来自 `SlabList<Node<M, K, V>>`，没有逐节点堆分配。

## 迭代与范围查询

B 树的数据分散在所有层级，无法像 B+ 树一样沿叶子链迭代。`BTree::iter()` 利用
节点中的父指针计算中序后继：内部项的后继是右子树最小项，叶子最后一项则沿父链
找到第一个“当前孩子不是最后一个孩子”的祖先。迭代器只保存当前 `(节点, 下标)`，
不使用工作栈，也不做任何堆分配。

`range` / `range_mut` 在构造迭代器时各用一次 `O(log n)` 搜索定位首、尾位置，之后
只保存这两个位置：

- B+ Tree 沿 `prev` / `next` 叶子链移动；
- B Tree 沿父指针计算中序前驱/后继；
- 不可变范围迭代器支持 `DoubleEndedIterator`（可以 `.rev()`）；
- 可变迭代器只交出 `&mut V`，key 与树结构保持不变；
- 所有迭代器状态都是固定大小的游标，不使用 `Vec`、`Box` 或工作栈。

因此新增的范围与可变迭代 API 不会为每次迭代引入临时堆分配。B 树的可变迭代器
使用字段级裸指针投影，只对目标项的 `value_` 字段建立 `&mut V`，避免与同一节点
中先前交出的其他 `&mut V` 产生别名。

# SlabList 与 SlotPtr

B+ Tree 使用 `SlabList<T, C>` 保存数据 `(K, V)` 和树节点 `TreeNode`；B Tree 则只
用 `SlabList<Node>` 保存节点，`(K, V)` 直接位于节点内部。`SlabList` 按 Chunk 批量
分配槽位；每次插入返回一个 `SlotPtr<T>` 句柄。`SlotPtr` 直接指向槽位中的元素，
因此树不需要再通过额外容器解引用。

树看到的只是 `SlabList<T, C>`、`SlotPtr<T>`，以及 `*slot_ptr`、`&mut *slot_ptr` 这样的基本操作。

配置类型 `Cfg` 实现 `TrConfig`，同时指定单 Chunk 字节数 `CHUNK_SIZE` 和
allocator 类型 `Allocator`；allocator 实例由树自己保存，`SlabList` 在分配/释放
Chunk 时按需借用 `&Cfg::Allocator`，因此 allocator 不需要实现 `Clone`。两棵树默认
使用 `DefaultSlabConfig`，即 `SlabListConfig<DEFAULT_CHUNK_BYTES, Global>`（64 KiB
Chunk + `Global`）。B+ Tree 的 data arena 和 node arena 共用同一个 `CHUNK_SIZE`。

当前结构可以概括为：

```text
BPlusTree
   │
   ├── data SlabList
   │       └── (K, V)
   │
   └── node SlabList
           └── TreeNode

BTree
   │
   └── node SlabList
           └── Node
                   └── (K, V) + children
```

`SlabList` 是树的存储边界；两棵树都不需要知道 Chunk 内部如何组织。

`SlabList::remove` 在某个 Chunk 完全空闲时会尝试归还内存：如果它是链表中唯一
的 Chunk，则保留；否则只要它的前驱或后继也完全空闲，就把当前 Chunk 摘链并交给
allocator 释放。这是一次局部回收决策，不保证链表中绝对没有相邻的空 Chunk；它
保留了“空 arena 仍可继续插入而不立即重新分配”的缓冲。释放 Chunk 需要 allocator
实例，因此 `remove` 与 `clear` 一样按需借用 `&Cfg::Allocator`。

两棵树的实现代码只允许通过 `SlabList` 进行堆分配：节点、数据（B+ Tree）和
遍历状态都不使用 `Vec`、`Box` 等额外堆容器。B+ Tree 迭代沿叶子链，B Tree
迭代沿父指针，两者都不需要工作栈。

# Typed Slot Handle

`SlotPtr<T>` 的核心作用是把裸指针变成带有类型信息的句柄，它表示“某个 `SlabList<T>` 槽位中对象的地址”，本身不拥有 `T`。

因此 `SlotPtr<(K, V)>` 与 `SlotPtr<TreeNode<M, K, V>>` 虽然底层都是指针，但在类型系统中属于完全不同的类型，`Data Handle` 和 `Node Handle` 不会被意外混用。

同时，`SlotPtr<T>` 本身不要求 `T: Copy` 或 `T: Clone`；它只是 `Copy` 的指针句柄。

---

# Comparer 与 SlotPtr 的组合

Comparer 不仅可以比较实际数据 `K ↔ K`，也可以通过 SlotPtr 适配器参与 `SlotPtr<K> ↔ SlotPtr<K>`，或者异构地比较 `SlotPtr<L> ↔ SlotPtr<R>`。

其基本思想是 `SlotPtr` → `SlabList` → 实际对象 → `Comparer` → `Ordering`。这使得“数据”“数据的引用”“查询对象”都可以进入统一的排序关系。

因此 Comparer 并不是一个单纯替代 `Ord` 的小接口，而是整个索引结构的基础抽象。

---

# 查询 API

BPlusTreeCmp 的查询模型不是 `tree.get(key)`，而更接近 `tree.get_with_comparer(&query, &comparer)`：查询对象 `Query` 通过 `Comparer<K, Q>` 与树中的 `K` 建立关系，因此同一个数据集合可以存在多个查询关系。

例如同一个 `User` 可以分别通过 `IdComparer`、`NameComparer`、`EmailComparer`、`BirthdayComparer` 建立查询关系；甚至可以直接通过 `User ↔ u64` 的 Comparer 查询，不需要改变 `User`，也不需要创建临时 `User`。

# 操作 API

```rust
use bplustree_cmp::{BPlusTree, OrdComparer};

let mut tree = BPlusTree::<4, _, u64, &str>::new().unwrap();

// 插入；重复 key 返回 ConflictInfo
let _ = tree.try_insert(1, "one"); // Err(ConflictInfo) 表示已存在

// 覆盖已有 value，返回旧 value
let old = tree.insert(1, "uno");

// 同构查询与异构查询
let pair = tree.get(1);
let pair = tree.get_with_comparer(&1u64, &OrdComparer::new());

// 按序迭代
for (key, value) in &tree {
    println!("{key}: {value}");
}

// 范围查询：不可变与可变迭代器
for (key, value) in tree.range(10..20) {
    println!("{key}: {value}");
}
for (_, value) in tree.range_mut(10..20) {
    *value += 1;
}

// key/value 视图与可变迭代
let keys: Vec<u64> = tree.keys().copied().collect();
for value in tree.values_mut() {
    *value += 1;
}

// 删除：remove 返回 value，remove_entry 返回 (K, V)
let value = tree.remove(1);
let entry = tree.remove_entry(2);

// 从已有集合构建
let tree = BPlusTree::<4, _, u64, &str>::from_iter_with_comparer(
    OrdComparer::new(),
    vec![(2, "two"), (1, "one")],
).unwrap();
```

`try_insert_with_comparer` / `get_with_comparer` / `remove_with_comparer` /
`range_with_comparer` 接受一个异构 Comparer，因此查询对象或范围边界可以是
`&str`、`u64` 等与 `K` 不同的类型。`factory` 只在确认没有等价 key 后调用一次，
避免为一次失败的插入构造临时 `K`。

范围边界遵循树自身的 Comparer 顺序：反向 Comparer 下 `range(20..10)` 表示
Comparer 意义上的 `20 <= key < 10`，与 `i32` 的自然顺序无关。若边界顺序在
Comparer 下已经为空（例如普通 Comparer 下的 `20..10`），则返回空迭代器。

构造器遵循 `std::collections` 的命名：

- `K: Ord` 时使用 `new()` / `new_in(allocator)`，自动采用 `OrdComparer<K>`；
- 自定义 comparer 使用 `with_comparer(comparer)` /
  `with_comparer_in(comparer, allocator)`；
- 从已有集合构建使用 `from_iter_in(iter, allocator)`、
  `from_iter_with_comparer(comparer, iter)` 或
  `from_iter_with_comparer_in(comparer, iter, allocator)`。

这些构造器以及 `FromIterator` 都返回 `Result<_, TreeError>`（`FromIterator` 在
内部配置失败时 panic）。`TreeError` 是公开的树级错误类型，内部包装不会对外暴露
的 SlabList 配置错误。

# 配置与 Allocator

两棵树的公开类型都带有最后一个泛型参数 `Cfg: TrConfig`：

```rust
pub struct BPlusTree<const M: usize, C, K, V = (), Cfg = DefaultSlabConfig>;
pub struct BTree<const M: usize, C, K, V = (), Cfg = DefaultSlabConfig>;
```

`Cfg` 同时指定：

- 单 Chunk 的分配字节数 `Cfg::CHUNK_SIZE`；
- 分配 Chunk 使用的 allocator 类型 `Cfg::Allocator`。

树自身持有 `Cfg::Allocator` 实例，内部 arena 在分配或释放 Chunk 时借用
`&Cfg::Allocator`，因此 allocator 不需要实现 `Clone`，也不要求是 ZST。
`TrConfig` 是开放的 trait：使用者既可以使用内置的 `SlabListConfig`，也可以自行
实现配置类型。

只选择 Chunk 大小、继续使用 `Global`：

```rust
use bplustree_cmp::{BPlusTree, OrdComparer, SlabListConfig};

type SmallTree = BPlusTree<4, OrdComparer<u64>, u64, u64, SlabListConfig<4096>>;

let mut tree = SmallTree::new().unwrap();
tree.insert(1, 10);
assert_eq!(tree.get(1), Some((&1, &10)));
```

只替换 allocator、保持默认 64 KiB Chunk：

```rust
use bplustree_cmp::{DefaultSlabConfig, OrdComparer, BPlusTree};

type TreeWithAlloc =
    BPlusTree<4, OrdComparer<u64>, u64, u64, DefaultSlabConfig<MyAlloc>>;

let tree = TreeWithAlloc::new_in(my_alloc).unwrap();
```

同时替换 Chunk 大小与 allocator：

```rust
type Tree =
    BPlusTree<4, OrdComparer<u64>, u64, u64, SlabListConfig<4096, MyAlloc>>;
```

`CHUNK_SIZE` 是 Chunk 总分配字节数，不是“刚好容纳多少个元素”的槽位数。不同
`T` 会得到不同槽位数；配置过小导致连一个槽位都放不下时，树构造返回
`TreeError`。常见的 2 的幂大小（1 KiB、4 KiB、64 KiB 等）只是建议，不是限制，
`TrConfig` 保持开放。

crate 同时导出 `CHUNK_SIZE_1K`、`CHUNK_SIZE_2K`、`CHUNK_SIZE_4K`、
`CHUNK_SIZE_8K`、`CHUNK_SIZE_16K`、`CHUNK_SIZE_32K`、`CHUNK_SIZE_64K`
作为推荐档位，例如 `SlabListConfig<CHUNK_SIZE_4K>`。这些常量只是建议，不是
限制；`TrConfig` 保持开放，使用者仍可实现自己的配置。

# 设计原则

BPlusTreeCmp 的设计可以归纳为以下原则：

### 1. 数据不负责排序

`Data ≠ Ordering Policy`，排序关系由 Comparer 定义。

### 2. Index 不拥有 Key

Index 保存数据引用，而不是 Key 副本。

### 3. 查询不需要构造 Key

查询类型可以与 Key 完全不同。

### 4. Key 不需要 Clone

索引结构只保存 SlotPtr，不复制实际 Key。

### 5. Data 与 Index 分离

数据和树节点分别存储，通过 `SlotPtr<T>` 连接。

### 6. SlabList 与 B+ Tree 解耦

树只依赖 SlabList 抽象，而不依赖具体底层容器。

### 7. B+ Tree 负责结构，Comparer 负责顺序

B+ Tree 负责：

* 平衡结构
* 子节点组织
* 节点分裂与合并
* 搜索路径
* 叶节点组织

Comparer 负责：

* 小于
* 等于
* 大于
* 数据与查询之间的排序关系

# 与传统 `Ord` 型 B+ Tree 的区别

|                 | 传统设计         | BPlusTreeCmp            |
| --------------- | ------------ | ----------------------- |
| 排序关系            | Key 自己定义     | Comparer 定义             |
| `K: Ord`        | 通常需要         | 不需要                     |
| Key Clone       | 可能用于索引 Key   | 不需要                     |
| Index Separator | 通常保存 Key     | 保存数据引用                  |
| 查询类型            | 通常与 Key 紧密相关 | 可以完全不同                  |
| 异构查询            | 依赖额外机制       | `TrComparer<K, Q>` 原生支持 |
| 一个数据类型的多个排序     | 通常需要额外包装     | 可以提供多个 Comparer         |
| 数据与索引           | 容易耦合         | 明确分离                    |
| 底层存储            | 通常由结构直接决定    | 通过 SlabList 抽象             |

# 性能对比 Benchmark

`benches/btreemap_compare.rs` 使用相同的随机 key 插入顺序、查询序列和删除顺序，
对比以下三类有序映射：

* `BPlusTree`（`M = 4`、`M = 16`）；
* `BTree`（`M = 4`、`M = 16`）；
* `std::collections::BTreeMap<u64, u64>`。

覆盖六类常见操作：`insert`、`lookup hit`、`lookup miss`、`update`（通过
`get_mut` 修改 value）、`iterate`（按 key 升序遍历）与 `remove`。

```text
cargo bench --bench btreemap_compare
BENCH_N=500000 BENCH_SAMPLES=7 cargo bench --bench btreemap_compare
```

表中数值为多次采样的中位数，单位是 ns/op（每次操作纳秒数），越小越好。以下是一次
`N = 200000`、`samples = 5` 的本机运行结果，仅用于观察数量级：

| operation   | B+Tree(M=4) | B+Tree(M=16) | BTree(M=4) | BTree(M=16) | BTreeMap |
| ----------- | ----------: | -----------: | ---------: | ---------: | -------: |
| insert      |     1803.97 |      1618.65 |    1407.00 |    1178.89 |   429.19 |
| lookup hit  |     1918.24 |      1785.82 |    1134.49 |     937.91 |   465.51 |
| lookup miss |      156.29 |        96.07 |     149.51 |      93.16 |   118.25 |
| update      |     1916.64 |      1788.81 |    1149.53 |     938.11 |   468.00 |
| iterate     |       94.00 |        67.41 |      71.48 |      38.33 |    29.30 |
| remove      |     2047.12 |      1864.36 |    1523.25 |    1227.23 |   611.26 |

相对 `BTreeMap` 的倍数：

| operation   | B+Tree(M=4) | B+Tree(M=16) | BTree(M=4) | BTree(M=16) |
| ----------- | ----------: | -----------: | ---------: | ---------: |
| insert      |       4.20x |        3.77x |      3.28x |      2.75x |
| lookup hit  |       4.12x |        3.84x |      2.44x |      2.01x |
| lookup miss |       1.32x |        0.81x |      1.26x |      0.79x |
| update      |       4.10x |        3.82x |      2.46x |      2.00x |
| iterate     |       3.21x |        2.30x |      2.44x |      1.31x |
| remove      |       3.35x |        3.05x |      2.49x |      2.01x |

几个符合设计预期的现象：

* `M = 16` 通常比 `M = 4` 更快：树更浅、节点内二分次数略增，但缓存/指针跳转减少；
* B+ Tree 的命中查询比 B Tree 慢：B+ 索引中的 key 是 `SlotPtr<(K, V)>`，每次比较
  都要解引用到 Data SlabList；B Tree 把 key 直接放在节点里，因此命中查询更快；
* 两者的命中查询仍慢于 `BTreeMap`：Comparer 是动态分派点，节点布局与分配方式也
  不同于标准库的紧凑节点；
* 未命中查询在 `M = 16` 时可以略快于 `BTreeMap`：树更浅，提前失败；
* 插入/删除需要维护 SlabList 节点、分裂/借位/合并以及 B+ Tree 的 separator，
  因此明显慢于 `BTreeMap`；
* B+ Tree 的迭代沿叶子链进行；B Tree 的迭代沿父指针计算中序后继，两者都不需要
  额外 `Vec`；B+ Tree 还需要逐个解引用数据句柄，因此迭代更慢；
* 对于 `String`、`Vec<u8>` 或大型结构体这类 Key，避免复制带来的收益可能抵消上述
  开销；具体应以实际 Key 类型的 benchmark 为准。

节点容量 `M` 是每个节点的最大项数，要求 `M >= 2`。B+ 树的非根节点最小占用为
`M / 2`（向下取整）；B 树的非根节点最小项数为 `ceil((M + 1) / 2) - 1`。
偶数 `M` 会得到对称分裂，奇数 `M` 仍然正确，只是填充率略不对称。

因此当前项目可以作为：

> **一种 Comparer-first、轻量索引、数据与排序关系解耦的 B+ Tree / B Tree 实现。**

它仍然不是标准库 `BTreeMap` 的完全替代品：allocator 与单 Chunk 大小已经通过
`Cfg: TrConfig` 暴露；此外尚未提供 `Entry` API、owned iterator、
`split_off` / `append` / `retain` / `pop_first` / `pop_last` 等更高层功能。范围查询、
可变迭代与 key/value 视图已经提供，并且都保持零临时堆分配。

# 一句话总结

如果只用一句话概括 BPlusTreeCmp：

> **B+ Tree 不需要拥有 Key，它只需要拥有能够根据 Comparer 找到正确位置的索引。**

Comparer 让 Key 不必定义自己的排序，也让查询可以完全异构；SlabList 和 SlotPtr 则让索引可以引用数据而不是复制数据。

最终形成：

```text
                 Comparer
                    │
                    ▼
             Ordering Relation
                    │
                    ▼
             ┌─────────────┐
             │  B+ Tree    │
             │             │
             │ lightweight │
             │   Index     │
             └──────┬──────┘
                    │
                 SlotPtr<T>
                    │
                    ▼
                  SlabList
                    │
                    ▼
                 (K, V)
```

**数据只有一个来源，索引只是引用，排序属于 Comparer，查询不必成为 Key。**

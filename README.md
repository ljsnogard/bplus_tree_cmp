# BPlusTreeCmp

> This document is generated by ChatGPT. I Read it, and I think it's great.

一个基于 **Comparer 定义顺序** 的 Rust B+ 树实现。

本项目试图回答一个看似简单、实际上非常重要的问题：

> **B+ 树为什么一定要把 Key 本身当成排序对象？**

传统的 `BTreeMap<K, V>` 思路通常是：

```text
K 必须能够自己比较自己
        ↓
树保存 K
        ↓
搜索时拿另一个 K 与它比较
```

而本项目采取完全不同的设计：

```text
                    Comparer
                       │
             定义“什么叫有序”
                       │
                       ▼
        ┌──────────────────────────┐
        │        B+ Tree           │
        │                          │
        │  Index → Data reference  │
        │  Leaf  → actual data     │
        └──────────────────────────┘
```

**Key 不负责定义自己的顺序。**

树只负责保存数据和索引结构，而“两个对象应该如何排序”完全由外部 `Comparer` 决定。

这不仅让 B+ 树摆脱了 `Ord` 等 trait bound，更重要的是，它使得 **异构查询、轻量索引以及零 Key 复制的内部节点设计**都可以自然地成为 B+ 树的一部分。

---

## 为什么是 Comparer？

排序本质上并不是数据对象的一种固有属性。

例如：

```text
User
├── id
├── name
├── email
└── birthday
```

同一个 `User` 可以有很多种完全合理的排序方式：

```text
按 id 排序
按 name 排序
按 email 排序
按 birthday 排序
```

如果把排序定义写进 `User` 的 `Ord`，实际上只能选择一种“默认世界观”。

而数据库索引早已证明：

> **数据和索引顺序本来就应该是两个不同的概念。**

本项目把这个思想直接应用到了 B+ 树：

```rust
pub trait TrComparer<A, B = A>
where
    A: ?Sized,
    B: ?Sized,
{
    fn compare(&self, a: &A, b: &B) -> Ordering;
}
```

因此：

```text
T
 │
 ├── 数据本身
 │
 └── Comparer
       │
       └── 定义 T 的某一种排序关系
```

`T` 不需要实现 `Ord`、`PartialOrd` 或 `Eq`。

甚至 `T` 根本不需要知道自己参与了什么排序。

Comparer 才是索引的真正定义。

---

# B+ 树真正需要的不是 Key，而是“可比较性”

传统 B+ 树的内部节点通常会被描述成：

```text
          [ K1 | K2 | K3 ]
          /    |    |    \
```

这很容易让人产生一个误解：

> 内部节点必须保存 Key。

其实并不是。

内部节点真正需要解决的问题只有一个：

> **当给定一个查询对象时，我应该进入哪个子树？**

如果可以比较：

```text
query ? child
```

就已经足够。

因此，本项目的内部节点设计是：

```text
IndexNode

children:
    TreeNodeId
    TreeNodeId
    TreeNodeId
    ...
```

而不是：

```text
IndexNode

keys:
    K
    K
    K
    ...

children:
    ...
```

源码中的 `IndexNode` 实际只保存子节点引用以及父节点引用；真正的数据存放在 `DataLeaf` 中。

这意味着：

> **索引节点根本没有必要拥有 Key。**

它只需要知道：

```text
这个引用指向哪里
```

以及通过 Comparer：

```text
这个引用所代表的数据与查询对象之间是什么顺序
```

# 轻量化的索引节点

这是本项目最重要的设计之一。

假设：

```rust
struct Key {
    data: String,
    ...
}
```

如果传统 B+ 树在每个内部节点复制一份 Key，那么一棵拥有大量数据的树可能会出现：

```text
Leaf:

    Key
    Value

    Key
    Value

    Key
    Value

       ...

Index:

    Key
    Child

    Key
    Child

    Key
    Child

       ...
```

于是同一个 Key 的信息可能同时存在于：

```text
叶节点
内部节点
更高层内部节点
```

Key 越大，这个问题越明显。

例如 Key 是：

```text
String
Vec<u8>
Arc<[u8]>
复杂结构
```

索引复制的成本就不再是一个可以忽略的问题。

## 本项目的结构

本项目把数据和树节点分开存储：

```text
data_arena
    │
    ├── T
    ├── T
    ├── T
    └── T

node_arena
    │
    ├── Root
    ├── Index
    ├── Index
    └── Leaf
```

树节点通过：

```rust
Idx<T>
```

引用 Arena 中真正的数据或节点。

`Idx<T>` 本质上只是一个带类型信息的索引，而不是一个拥有数据的 Key。

因此内部节点可以做到：

```text
IndexNode
    │
    ├── Idx<Node>
    ├── Idx<Node>
    ├── Idx<Node>
    └── ...
```

而不需要：

```text
IndexNode
    │
    ├── Key
    ├── Idx<Node>
    ├── Key
    ├── Idx<Node>
    └── ...
```

最终形成一种非常干净的关系：

```text
                  ┌───────────────┐
                  │    Comparer   │
                  └───────┬───────┘
                          │
                          │ compare
                          ▼
                 ┌────────────────┐
                 │   Index Node   │
                 │                │
                 │  Idx ──────────┼──────┐
                 │  Idx ──────────┼──┐   │
                 │  Idx ──────────┼┐ │   │
                 └────────────────┘│ │   │
                                   │ │   │
                                   ▼ ▼   ▼
                                ┌────────────┐
                                │   Leaf     │
                                │            │
                                │     T      │
                                │     T      │
                                │     T      │
                                └────────────┘
```

**索引节点只保存“指向数据的路径”，不保存数据本身。**

这正是 B+ 树非常适合做索引结构的原因。

# Comparer 最漂亮的地方：异构查询

如果 Comparer 只是为了替代：

```rust
a.cmp(b)
```

那么它的价值其实没有那么大。

真正让这个设计变得优雅的是：

```rust
TrComparer<A, B>
```

注意这里有两个类型：

```text
A ≠ B
```

也就是说：

```rust
compare(&A, &B)
```

完全合法。

这意味着：

> **树中的数据类型与查询类型不需要相同。**

---

## 一个非常典型的例子

假设树保存：

```rust
String
```

那么传统设计可能需要：

```rust
map.get("hello".to_string())
```

因为查询参数必须变成 `String`。

但使用 Comparer，可以直接：

```text
Tree:
    String
      ▲
      │
      │ compare
      │
Query:
    &str
```

也就是说：

```rust
TrComparer<String, str>
```

就可以完成查询。

查询对象甚至不需要拥有 Key。

# 更进一步：查询对象甚至可以完全不是 Key

假设树保存：

```rust
struct User {
    id: u64,
    name: String,
}
```

树按照：

```text
User.id
```

排序。

那么查询完全可以只使用：

```rust
u64
```

而不需要构造：

```rust
User {
    id: 123,
    name: String::new(),
}
```

比较关系可以直接定义为：

```text
User ↔ u64
```

于是：

```text
Tree data:

User { id: 1, ... }
User { id: 2, ... }
User { id: 3, ... }

Query:

3
```

Comparer 执行：

```text
User.id ? 3
```

即可。

这就是所谓的 **heterogeneous lookup（异构查询）**。

# `search_.rs` 已经体现了这种设计

本项目的搜索接口本身就没有把查询类型固定成 `T`：

```rust
pub fn search_resursive<'f, T, H, C, const M: usize>(
    node_idx: &'f TreeNodeId<T, M>,
    arena: &'f Arena<TreeNode<T, M>>,
    hint: &'f H,
    cmp: &'f C,
)
where
    C: TrComparer<T, H>,
```

这里：

```text
T = 树中保存的数据类型

H = 查询类型

C = T 与 H 之间的比较关系
```

因此搜索算法根本不需要：

```rust
H: Into<T>
```

也不需要：

```rust
H: Borrow<T>
```

更不需要：

```rust
H == T
```

它只需要：

```rust
C: TrComparer<T, H>
```

这是一种非常纯粹的抽象：

> **搜索算法不关心查询对象是什么，它只关心查询对象能不能与索引中的数据建立顺序关系。**

`search_.rs` 中还专门出现了 `DataIdxHeterComparer` 的设计雏形，说明这种异构比较并不是 API 层面的附加功能，而是整个搜索结构的一部分。

# `OrderedArray` 也是同一种思想

B+ 树节点内部需要维护一个小型有序数组。

本项目的 `OrderedArray` 并没有把搜索限制在：

```rust
T: Ord
```

而是提供：

```rust
search_by(&hint, &cmp)
```

其核心约束是：

```rust
TyCmp: TrComparer<T, TyHint>
```

二分搜索实际做的事情非常简单：

```text
node item
    │
    │ compare
    ▼
query hint
```

而不是：

```text
node item
    │
    │ 转换成 T
    ▼
query T
```

因此，同一个底层有序数组结构天然支持：

```text
T ↔ T
T ↔ &str
T ↔ u64
T ↔ Query
T ↔ Index
```

只要存在对应的 Comparer 即可。

# HomoComparer 与 HeteroComparer

当索引节点保存的是：

```rust
Idx<T>
```

它实际上并不知道 `T` 是什么。

如果要比较两个索引：

```text
Idx<T> ? Idx<T>
```

可以通过：

```text
Idx<T>
   ↓
Arena
   ↓
T
   ↓
Comparer
   ↓
Ordering
```

完成。

项目中的 `HomoIdxComparer` 正是这种适配器：它从两个 `Idx<T>` 找回 Arena 中的对象，然后调用原始 Comparer。

而异构情况下则可以进一步变成：

```text
Idx<T> ? Query
```

也就是：

```text
Idx<T>
   ↓
Arena
   ↓
T
   ↓
TrComparer<T, Query>
   ↓
Query
```

这让“索引引用”本身也可以参与 Comparer 体系。

这是一种非常重要的组合性：

> **Comparer 不仅可以比较数据，也可以比较数据的引用、索引和外部查询对象。**

# 数据、索引和排序三者彻底解耦

整个设计最终可以概括为三个独立的维度：

```text
             ┌─────────────┐
             │    Data     │
             │      T      │
             └──────┬──────┘
                    │
                    │ stored in
                    ▼
             ┌─────────────┐
             │    Arena    │
             └──────┬──────┘
                    │
                    │ referenced by
                    ▼
             ┌─────────────┐
             │    Index    │
             │   Idx<T>    │
             └──────┬──────┘
                    │
                    │ ordered by
                    ▼
             ┌─────────────┐
             │  Comparer   │
             └─────────────┘
```

这三个东西分别负责：

| 组件              | 负责什么   |
| --------------- | ------ |
| `T`             | 数据是什么  |
| `Idx<T>` / Node | 数据在哪里  |
| `Comparer`      | 数据如何排序 |

传统容器往往把这三件事部分耦合在一起。

本项目则把它们拆开。

# 为什么这是 B+ 树非常自然的设计？

B+ 树的核心职责其实不是“存 Key”。

它的职责是：

```text
把一个有序空间划分成很多连续区间
```

例如：

```text
                 [ 50 ]
                /      \
        < 50             >= 50
       /                     \
   [10,20,30]             [60,70,80]
```

`50` 的真正作用不是“存储一个 50”。

它真正表达的是：

```text
左边的数据 < 50
右边的数据 >= 50
```

因此，内部节点保存一个 Key 只是传统实现中最简单的表达方式。

如果我们已经有：

```text
Comparer
```

那么内部节点完全可以保存：

```text
指向某个实际数据的引用
```

然后通过：

```text
Comparer(data, query)
```

得到完全相同的区间判断。

于是：

> **内部节点保存 Key 并不是 B+ 树的本质，只是没有独立 Comparer 时的一种实现手段。**

本项目选择把这个实现细节彻底消除。

---

# 这种设计还有一个非常实际的优势：Key 不需要 Clone

对于：

```rust
u64
u32
usize
```

复制一个 Key 几乎没有成本。

但是对于：

```rust
String
Vec<u8>
Arc<[u8]>
大型结构
```

情况完全不同。

传统 B+ 树如果需要在内部节点维护分隔 Key，就会产生：

```text
叶节点拥有数据
        +
内部节点复制 Key
        +
更高层继续复制 Key
```

而本项目可以保持：

```text
Data:
    T T T T T T T T ...

Index:
    Idx Idx Idx Idx ...
```

所有实际数据只有一个来源。

内部节点只是引用这些数据。

因此 Key 越大、树越深、数据量越大，这种结构的优势越明显。

# Arena：让“引用而不拥有数据”成为可能

为了让这种设计成立，本项目没有让节点之间直接通过复杂的 Rust owning pointer 关系互相拥有。

而是使用 Arena：

```text
Arena<T>
    │
    ├── T
    ├── T
    ├── T
    └── ...
```

通过：

```rust
Idx<T>
```

引用其中的对象。

节点也同样存放在：

```rust
Arena<TreeNode<T, M>>
```

中。

因此：

```text
TreeNode
    │
    └── TreeNodeId
            │
            └── Arena
                    │
                    └── TreeNode
```

形成一种稳定、明确的关系。

当前实现中的 Arena 基于 `slab` 保存对象，而 `Idx<T>` 本身只包含一个索引值和类型标记。

这也为未来进一步实现：

* 节点分裂
* 节点合并
* 删除
* 迭代器
* 范围查询
* 更复杂的索引结构
* 不同的内存管理策略

留下了清晰的基础。

# 一个更值得关注的 API：`get_by`

最终理想中的使用方式并不是：

```rust
tree.get(key)
```

而应该是：

```rust
tree.get_by(&query, &comparer)
```

也就是：

```text
Tree<T>
     │
     │
     ├── 保存 T
     │
     └── 查询 H
             │
             ▼
        Comparer<T, H>
```

这意味着一个 B+ 树可以拥有：

```text
一个数据集合
+
任意数量的查询方式
```

例如：

```text
User
 │
 ├── IdComparer
 ├── NameComparer
 ├── EmailComparer
 └── BirthdayComparer
```

甚至：

```text
User
 │
 └── UserIdQueryComparer
```

查询时：

```text
u64
   ↓
UserIdComparer
   ↓
User
```

而不需要制造一个假的 `User`。

这比简单地给 `BPlusTree<K, V>` 加一个自定义 `Ord` 更彻底。

# Comparer 也意味着“索引”成为一等公民

从这个角度来看：

```text
BPlusTree<T, C>
```

其实并不是：

```text
Map<Key, Value>
```

而更接近：

```text
OrderedIndex<Data, OrderingRelation>
```

即：

> **一个由某种排序关系定义的索引。**

这与数据库中的思想更加接近。

数据本身：

```text
T
```

是一回事。

索引：

```text
Comparer<T, Q>
```

是另一回事。

查询：

```text
Q
```

又是第三回事。

三者不必相同。

这正是复杂数据结构真正需要的抽象层次。

# 设计原则

本项目遵循以下几个核心原则。

### 1. 数据不负责排序

```text
T ≠ ordering policy
```

排序关系由 Comparer 提供。

---

### 2. Index 不拥有 Key

内部节点尽可能只保存：

```text
Idx<TreeNode>
```

而不是复制：

```text
T
```

---

### 3. 查询不需要构造 Key

查询可以是：

```text
T
&str
u64
Query
其他类型
```

只需要提供：

```rust
TrComparer<T, Query>
```

---

### 4. 数据和索引分离

数据：

```text
data_arena
```

树节点：

```text
node_arena
```

通过类型化索引连接。

---

### 5. B+ 树只负责结构

B+ 树本身负责：

```text
平衡
节点分裂
节点连接
搜索路径
叶节点顺序
```

而不负责定义：

```text
什么叫“小”
什么叫“大”
什么叫“相等”
```

这些全部属于 Comparer。

# 与传统 `Ord` B+ 树的核心区别

| 传统设计          | BPlusTreeCmp                 |
| ------------- | ---------------------------- |
| `K` 自己定义顺序    | `Comparer` 定义顺序              |
| 通常要求 `K: Ord` | `T` 不需要 `Ord`                |
| 查询通常是 `K`     | 查询可以是任意 `Q`                  |
| `K` 与查询类型容易耦合 | `TrComparer<T, Q>` 天然支持异构查询  |
| 内部节点常保存分隔 Key | 内部节点可以只保存引用                  |
| Key 可能在索引层重复  | 实际数据只保存一份                    |
| 数据和索引容易耦合     | Data / Index / Ordering 三者分离 |
| 排序方式通常是类型固有属性 | 一个数据类型可以拥有多个索引关系             |

# 最核心的思想

如果只用一句话概括这个项目：

> **B+ 树不应该知道 Key 是什么，它只应该知道如何通过一个 Comparer 判断应该走向哪里。**

因此：

```text
             Comparer
                │
                ▼
       ┌─────────────────┐
       │    B+ Tree      │
       │                 │
       │  lightweight    │
       │  index nodes    │
       └────────┬────────┘
                │
                ▼
             Arena
                │
                ▼
              Data
```

Comparer 让查询可以异构。

Arena 让数据可以集中拥有。

`Idx<T>` 让索引节点可以轻量化。

B+ 树本身则只承担它真正应该承担的工作：

> **维护一个高效的有序索引结构。**

这也是为什么本项目选择 **Comparer-first B+ Tree**：不是为了给传统 B+ 树增加一个自定义比较器参数，而是试图从根本上重新审视 **“B+ 树为什么需要保存 Key”** 这个前提。
